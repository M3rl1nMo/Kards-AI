# 模拟器已知问题与修改说明

更新日期：2026-10-09。本文整理当前对话中发现及本次源码核对得到的问题，不声称已审计全部卡牌。
源码注释使用同一 BUG 编号。BUG-01～05 已修复，BUG-06 补充玩家观测，BUG-07 新增安全编号与玩家动作接口，BUG-08 默认严格拒绝未支持效果。
BUG-08 的修复是阻止错误样本继续使用，不代表所有未支持卡牌效果都已实现。BUG-09 已按用户确认的“费用增减与交换独立生效”规则修复；BUG-10～12 仍待处理。
历史覆盖报告、`implemented` 标记和无报错对局均不能独立证明游戏规则正确。

## BUG-01：DILEMMA 找错单位（已修复）

- 位置：`simulator/rules/native.py`，`swap_attack_opcost` 分支。
- 原因：条件与查找使用 `source_unit_id`；DILEMMA 是指令，只有目标单位 ID，没有来源单位 ID，因此跳过执行并落入兜底。
- 修改：两处均改为 `context.target_unit_id`。
- 理由：本地卡牌说明是交换目标单位的攻击力与行动费用，应修改目标而不是来源。
- 验证：覆盖友方、敌方目标；不能把所有效果中的 source 全局替换成 target。

## BUG-02：重复交换读取旧行动费用（DILEMMA 路径已修复）

- 位置：`native.py` 交换分支，以及 `simulator/actions/action.py` 的 `_operation_cost`。
- 原因：交换时不断追加 `set_operation_cost`，读取时 `next(...)` 取第一条旧值。
- 修改：交换分支删除所有旧设置费用记录，再添加新记录，保留其他类型修正。
- 理由：让读取方拿到唯一当前设置值，避免改变所有卡牌的费用优先级。
- 示例：攻击 4、行动费 0 → 第一次 0/4 → 第二次应恢复 4/0；旧代码第二次得到 4/4。
- 验证：`tests/test_dilemma.py` 覆盖两种目标归属、攻击 0/4/7、连续两次交换及保留无关修正。
- 限制：其他写入者及临时费用恢复机制还需独立核对。
- 后续 BUG-09 修复：读取费用改为最新设置值加独立增减；DILEMMA 仍清理旧设置记录，确保只保留一个交换基准。

## BUG-03：手动换牌结束后首回合没有初始化（已修复）

- 位置：`Simulator.reset`、`MulliganAction.execute`。
- 原因：换牌结束后的恢复 p1 和 `start_turn(draw_card=False)` 只在自动路径执行。默认手动顺序 p1→p2 后仍停在 p2，初始资源没有正常准备。
- 修改方法：统一换牌结束入口；最后一人完成时切回 p1 并启动首回合，删除自动路径中重复启动的代码。
- 理由：自动和手动两条路径应得到一致的首回合状态。
- 验证方法：对比两条路径保留起手牌后的当前玩家、资源、回合号和抽牌次数，确保不额外抽牌或启动两次。
- 实际修改：最后一次 MulliganAction 切回 p1 并 start_turn(draw_card=False)，移除 reset 自动路径重复启动。自动/手动同种子状态完全一致，首回合仅启动一次。

## BUG-04：输掉对局的行动方也可能获得终局正奖励（已修复）

- 位置：`Simulator.step_fast`。
- 原因：非平局就加 100，没有检查胜方是否是 `action.player_id`；结束回合引发疲劳等情况可能使行动方输掉对局。
- 修改方法：从 game_status 得到胜方，行动方胜利给正奖励、失败给负奖励；平局和掉血奖励分别定义。
- 理由：训练目标必须与行动方实际胜负一致。对局结算不会因此变错，错误在返回的训练奖励。
- 验证方法：主动获胜、行动后自己失败、平局三种情形；训练器明确回报视角，不直接混用奖励与胜负标签。
- 实际修改：胜方等于 action.player_id 加 100，否则减 100；平局无终局加分。掉血奖励保留原语义，胜/负/平三种返回值已测试。

## BUG-05：动作选项条件表达式作用范围错误（已修复）

- 位置：`Simulator.get_available_actions` 的 `selected_options`。
- 原因：Python 条件表达式右结合，现有表达式会先判断 has_high_attack；有高攻击单位时，普通 develop 卡也只得到 `[None]`。
- 修改方法：写成 `([None] if has_high_attack else ["blitz", "shock"]) if spec.shock_tactics else (None, *spec.develop_options)`，或改成清楚的 if/else。
- 理由：高攻击力条件只应影响 shock_tactics，不能删除其他卡的合法选项。
- 验证方法：有/无高攻击单位时分别枚举 shock_tactics 和 develop 卡，检查动作完整性。
- 实际修改：内部三元表达式加括号；高攻击单位存在时，其他卡的选项不再被强制替换为 None，新增回归测试通过。

## BUG-06：玩家观测遗漏可见信息（已补充，后续按卡牌扩展）

- 位置：`get_observation`、`_observation_player`。
- 原因：观测没有自身 active_countermeasures，也没有完整呈现单位关键词、费用修正等状态。
- 修改方法：按真实玩家可见范围补齐字段，并提供独立观测编码；不要直接把完整 state 输入网络。
- 理由：神经网络需要知道自己的可见状态，否则难以区分效果不同的局面。
- 验证方法：己方能看到自身反制及修正，对方仍看不到秘密；每种动态效果有正确可见表示。
- 实际修改：补充己方反制、卡牌费用规则、单位修正、状态、基础能力和当前行动费用；敌方只开放白名单状态，隐蔽单位能力及属性仍隐藏。返回值复制，修改观测不会修改对局。
- 边界：不是完整的全卡池观测规范，新效果仍须单独审查可见性。

## BUG-07：单位实例 ID 可能泄露隐蔽单位身份（玩家接口已修复）

- 位置：玩家观测的单位 `id`、前线/支援线列表，以及动作目标 ID。
- 原因：隐蔽单位虽然隐藏 card_id，但仍暴露实例 ID；若实例 ID 带卡牌名称，仍可能推断身份。
- 修改方法：先检查部署、生成与回放的 ID 格式；必要时统一改用无卡名编号，或建立玩家视角编号映射。
- 理由：隐藏信息需要同时检查所有可见字段和合法动作，不只检查 hand。
- 验证方法：把隐蔽单位身份改变后，对手可见输出不应额外揭露卡名；动作映射仍能指向同一单位。
- 实际修改：观测以 unit-1 等稳定编号替代原始 ID，包括战场列表；新增 get_player_actions()/step_player() 同步映射目标及攻击者，验证可正常执行。
- 接口要求：网络使用 get_observation + get_player_actions + step_player。get_available_actions/step_fast 仍是裁判内部接口，包含原始 ID，禁止把原始动作直接编码给网络。完整搜索信息集和合法动作推断泄漏仍需另行审计。

## BUG-08：效果落入未支持分支后游戏继续（严格拒绝已修复，卡牌实现仍待排查）

- 位置：`simulator/effects/resolver.py` 的 `unsupported_effect`；`native.py` 各种带条件的效果分支。
- 原因：兜底只记录日志，未执行对应效果但继续对局；上游原因可能是功能缺失、目标未传入、解析错误或执行分支限制。
- 修改方法：训练采用严格检查，触发后丢弃整局并保存种子、卡组及完整动作序列；逐卡重现后修复解析/上下文/执行层，保留调试日志模式。
- 理由：缺失抽牌、修复等效果会产生错误收益，污染训练数据。
- 历史例子：second_chance/draw_matching、cobelligerents/return_to_deck、komet/return_to_hand、42nd_rifles/repair、37mm_m1_aa_gun/set_attack、40_royal_marine/grant_trait。
- 说明：这些效果有的已有部分执行代码，不能把日志解释成整个效果类型都未实现。draw_matching 分支只处理 unit/order；repair 分支需要 target_unit_id。
- 验证方法：检查预期状态变化、费用消耗和事件，不只检查没有报错。
- 实际修改：Simulator 默认 strict_effects=True，step/step_fast 检测新 unsupported_effect 并抛出 UnsupportedEffectError，标记整局无效，禁止继续行动，必须 reset。异常发生时动作已经修改状态，没有回滚；整局样本必须丢弃。
- 重现信息：异常 report 保存随机种子、初始裁判状态、动作类型与字段以及未支持效果，可用 JSON 保存。这些包含隐藏信息，仅供调试，不得交给玩家网络。
- 调试模式：strict_effects=False 保留原日志行为；此模式下出现未支持记录的对局不可用于训练。
- 另外修复：resolver 条件函数错误使用 @staticmethod 却访问 self.cards，已改为实例方法并加入测试。

## BUG-09：设置费用屏蔽增减、交换忽略当前费用（已修复）

- 位置：`native.py` 交换分支的 base_op 计算。
- 原因：目前只取卡牌基础费用及设置值，没有加减费用修正，也没复用 `_operation_cost` 的特殊状态处理。
- 确认规则：用户明确费用增减与交换独立生效，应交换当前实际数值。
- 实际修改：_operation_cost 使用最新设置值或基础费用，再叠加费用增减，最后限制不低于 0；交换分支复用该函数读取当前费用。
- 避免重复叠加：交换后的设置基准写为“原攻击力减已有费用增减总和”，保留增减记录及来源；读取时再加回已有增减，结果恰好等于原攻击力。未来新增增减仍正常生效。
- 理由：不能忽略费用增减，也不能简单把原攻击力作为基准后重复加上已有增减；不能删除带来源的修正而破坏后续移除/失效处理。
- 验证方法：基础费用、费用增加、费用减少、设置费用和特殊状态分别测试。当前 100 局简单卡组不能证明这些组合正确。
- 修复前：初始 4/0，交换为 0/4；再加/减行动费 1 仍读到 4，再交换为 4/0。原因是设置值提前返回，以及交换分支忽略增减。
- 修复后：初始 4/0 → 交换 0/4 → 费用 +1 得 0/5 → 再交换 5/0；费用 -1 则为 0/3 → 再交换 3/0。二次交换后再费用 +1 得到行动费 1，证明新增修正仍生效。
- 攻击修正：以初始行动费 1 的单位测试，交换后攻击为 1；攻击 +1/-1 后再交换，新行动费分别为 2/0，测试通过。
- 测试状态：移除两个 expectedFailure 标记，并增加交换前已有增减、连续交换保留来源以及最新设置值和增减共同生效的测试，全部通过。隐蔽状态固定行动费 1 的已有特殊规则保留，其他动态光环/转换组合仍应逐卡验证。

## BUG-10：规则 implemented 标记不等于可训练卡池（验证缺口）

- 位置：`training/preflight.py` 的 `eligible_card_ids`。
- 原因：按静态状态标记准入，但已标记卡牌仍可能触发 BUG-08。
- 修改方法：以逐卡规则测试和已验证固定卡组维护准入名单；未验证效果隔离，运行时保留严格检查。
- 理由：解析识别、代码分支存在和实际规则正确是不同的证据。
- 验证方法：准入卡牌涉及的触发器、目标、数量和状态组合都有定向用例。

## BUG-11：默认冒烟测试卡池与正式国家规则不一致（验证缺口）

- 位置：`run_preflight` 默认 nation="France"；随机卡组工具默认未开启正式国家校验。
- 原因：法国在当前项目的正式国家列表中是盟国，默认检查只覆盖这一卡池。
- 修改方法：正式测试使用 Britain/Germany/USA/Soviet/Japan 为主国，覆盖合法盟国组合，并验证 Simulator.reset 的国家准入。
- 理由：单一卡池通过不代表五个主国都可以训练。
- 验证方法：合法组合接受，非法主国拒绝；各主国都执行效果覆盖测试。

## BUG-12：最后一步终局可能被漏计（统计缺口）

- 位置：`run_preflight` 的动作循环。
- 原因：terminal_episodes 只在下一次迭代顶部累加，最后一个允许动作刚好结束游戏时不会再迭代。
- 修改方法：把终局计数放到循环结束后，每局仅计一次；未结束时单独记录 truncated。
- 理由：执行上限、正常终局和平局必须区分，避免给训练器错误标签。
- 验证方法：最后一步获胜仍计为终局；达到上限但未结束的对局标记截断。

## 已执行的测试与边界

这些测试证明该简单卡组内的交换路径可用，不证明全卡池、所有费用组合、隐藏信息处理或训练奖励正确。

随后修复 BUG-09，共 220 项单元测试全部通过，无预期失败；测试覆盖费用和攻击增减、重复交换、交换前已有修正及来源保留。
旧的 `needs_kards_confirmation.md` 等清单保留为历史排查线索，具体项目须按当前源码和游戏重新确认，不能照单认定全部为当前缺陷。
